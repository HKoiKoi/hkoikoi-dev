# Git 커밋

변경사항을 분석해 이 프로젝트의 커밋 관례에 맞는 한국어 커밋 메시지를 만들고, 사용자가 커밋을 요청했다면 커밋까지 수행한다. 커밋 기록은 나중에 변경 이유를 추적하는 자료이므로, 일관된 형식과 "한 커밋 = 한 논리적 변경"이 핵심이다.

## 요청 유형 판단

| 요청                                            | 동작                                                   |
| ----------------------------------------------- | ------------------------------------------------------ |
| "커밋 메시지 만들어줘", "메시지만"              | 메시지를 코드블록으로 제시하고 **멈춘다** (커밋 금지)  |
| "커밋해줘", "commit this"                       | 워크플로 전체 수행 (add → commit → 결과 확인)          |
| "커밋 나눠줘", 성격이 다른 변경이 섞여 있음     | 분리안 제시 → 확인 후 순서대로 여러 번 커밋            |
| "amend", "메시지 수정"                          | [amend 규칙](#amend와-히스토리-수정) 참고              |
| "push", "PR"                                    | 이 스킬 범위 밖. 사용자가 명시적으로 요청할 때만 수행  |

애매하면 커밋하지 않고 메시지만 제시한다. 커밋은 되돌릴 수 있지만, 의도치 않은 커밋은 신뢰를 깎는다.

## 워크플로

1. **현재 상태 파악** (병렬 실행)
   - `git status`: staged / unstaged / untracked 구분
   - `git diff --staged`: 커밋 대상. staged가 없으면 `git diff`로 전체 변경 확인
   - `git log -5 --format=%B---`: 최근 메시지 스타일 확인. 이 저장소의 관례가 이 문서보다 우선한다.
     - **커밋이 하나도 없으면**(`does not have any commits yet`) 이 문서의 규칙을 그대로 따른다. [첫 커밋](#첫-커밋--대량-변경) 절도 확인한다.
   - untracked 파일이 많으면 `git status --short`로 윤곽을 먼저 잡고, 필요한 파일만 내용을 확인한다.
2. **분석**: 무엇이 바뀌었는지(기능 추가 / 버그 / 리팩토링 / 문서 / 설정)와 왜 바뀌었는지 파악한다. diff만으로 "왜"가 불분명하면 추측해 쓰지 말고, 본문을 생략하거나 사용자에게 묻는다.
3. **분리 판단**: 성격이 다른 변경(예: 기능 + 문서 + 설정)이 섞여 있으면 커밋을 나눌 것을 제안하고, 파일 단위로 어떻게 묶을지 제시한다. 나누면 `git revert`·리뷰·이력 검색이 쉬워진다.
   - 한 파일 안에 성격이 다른 변경이 섞여 있으면 `git add -p`로 hunk 단위로 나눌 수 있다. 단, 대화형 모드는 이 환경에서 지원되지 않을 수 있으므로, 어렵다면 한 커밋으로 묶고 이유를 알린다.
4. **안전 점검**: 커밋 전 아래를 확인한다.
   - `.env*`(`.env.example` 제외), `*.pem`, 키/토큰/인증서/`credentials*` 파일이 변경 목록에 있으면 **제외하고 사용자에게 알린다**.
   - `node_modules/`, `.next/`, `*.tsbuildinfo` 등 빌드 산출물이 포함되어 있으면 제외하고, `.gitignore`에 빠졌다면 알린다.
   - diff에 하드코딩된 시크릿(Supabase `service_role` 키, API 키, 토큰 등)이 보이면 커밋하지 않고 즉시 알린다. 한 번 커밋되면 히스토리에 남는다.
5. **메시지 작성**: 아래 규칙을 따른다.
6. **커밋 수행** (사용자가 커밋을 요청한 경우에만)
   - 대상 파일을 이름으로 지정해 `git add <파일...>` 한다. `git add -A`/`.`는 의도치 않은 파일이 섞일 수 있어 피한다. 사용자가 "전부 커밋"이라고 해도 4번 점검을 먼저 통과시킨 뒤 파일 목록을 명시한다.
   - 이미 staged된 내용이 있고 사용자가 그것만 커밋하길 원하는 듯하면, 추가로 `add`하지 않고 staged 그대로 커밋한다.
   - 여러 줄 메시지는 HEREDOC으로 전달한다.

     ```bash
     git commit -m "$(cat <<'EOF'
     feat: 제목

     - 본문

     Co-Authored-By: ...
     EOF
     )"
     ```

   - pre-commit hook이 실패하면 원인을 고치고 다시 `add` 후 **새 커밋**을 만든다. 실패한 커밋은 만들어지지 않았으므로 `--amend`는 직전의 다른 커밋을 덮어쓰게 된다. 이 저장소의 `.claude/hooks`와 git hook은 우회하지 않는다 (`--no-verify` 금지).
   - 분리 커밋이면 한 커밋이 끝날 때마다 `git status`로 남은 변경을 확인하고 다음 묶음으로 진행한다.
   - 커밋 후 `git status`와 `git log -1 --stat`으로 결과를 확인하고, 커밋 해시와 제목을 사용자에게 보고한다.
   - `push`는 사용자가 따로 요청할 때만 한다.
7. 커밋 요청이 아니라 "메시지만 만들어줘"라면 메시지를 코드블록으로 제시하고 멈춘다.

## 메시지 형식

```
<타입>(<스코프>): <제목>   ← 스코프는 선택, 없으면 `<타입>: <제목>`

<본문> (선택)

<트레일러> (선택)
```

- **언어**: 제목과 본문은 한국어. 코드 식별자·파일명·라이브러리명·명령어는 원문 그대로 쓴다 (`feat(ui): Button에 loading prop 추가`). 타입과 스코프는 영문 소문자.
- **스코프는 필요할 때만 쓴다.** 변경이 한 영역에 한정되어 있고, 스코프가 있으면 커밋 목록에서 영향 범위를 바로 알 수 있을 때 붙인다 (`feat(auth): 비밀번호 재설정 폼 추가`). 변경이 여러 영역에 걸치거나 제목만으로 범위가 분명하면 생략한다. 애매하면 생략하는 쪽이 일관성이 높다.
- **스코프 이름**은 소문자 영문 한 단어로, 아래 영역 중에서 고른다. 이력이 생긴 뒤에는 새 이름을 만들기 전에 `git log`에서 이미 쓰인 스코프를 확인해 같은 영역에 다른 이름이 생기지 않게 한다.

  | 스코프     | 영역                                                                  |
  | ---------- | --------------------------------------------------------------------- |
  | `ui`       | `components/ui/` (shadcn 컴포넌트)                                    |
  | `auth`     | 인증 관련: `app/auth/`, `components/*-form.tsx`, 로그인/로그아웃 버튼 |
  | `app`      | `app/` 라우트·페이지·레이아웃·전역 스타일 (인증 제외)                 |
  | `supabase` | `lib/supabase/` 클라이언트·미들웨어 설정                              |
  | `db`       | Supabase 마이그레이션, 스키마, RLS 정책                               |
  | `lib`      | `lib/` 유틸리티 (`utils.ts` 등, supabase 제외)                        |
  | `config`   | `next.config.ts`, `tsconfig.json`, `tailwind.config.ts`, ESLint 등    |
  | `deps`     | 의존성 추가/업데이트 (`package.json`, `package-lock.json`)            |
  | `claude`   | `.claude/`, `.mcp.json`, `skills-lock.json` 등 Claude Code 설정       |

  위 표에 없는 영역이 새로 생기면(예: `components/tutorial/`처럼 독립된 묶음) 영역을 대표하는 영문 한 단어를 쓰되, 이 표에 행을 추가해 이름이 갈라지지 않게 한다.

- 스코프는 하나만 쓴다. 두 개 이상이 필요하면 커밋을 나눌 신호인지 먼저 따져 본다.
- **제목**: 50자 안팎(한글 기준 35자 내외 권장), 마침표 없음, 명사형/간결체로 끝낸다 ("추가", "수정", "교체", "적용"). 한국어에서 "추가해라" 같은 명령형은 어색하고, "추가했음"처럼 과거형도 쓰지 않는다. "무엇을"이 드러나야 하고, "어떻게"는 본문에 둔다.
- **본문**: 제목만으로 의도가 전달되지 않을 때만 쓴다. 한 줄 띄우고 불릿으로 "무엇을, 왜" 위주로 적는다. 변경 파일 목록을 나열하는 것은 diff가 이미 보여주므로 불필요하다. 한 줄은 72자 안팎에서 줄바꿈한다.
- **Breaking change**: 호환성을 깨는 변경은 타입 뒤에 `!`를 붙이고(`feat(db)!: ...`), 본문 끝에 `BREAKING CHANGE: 영향과 마이그레이션 방법`을 적는다. DB 컬럼 삭제·환경 변수 이름 변경처럼 배포 시 조치가 필요한 변경이 해당한다.
- **트레일러**: 이슈 참조는 `Fixes #123`(닫음) / `Refs #123`(참조만). 세션이 커밋 attribution 트레일러(예: `Co-Authored-By: ...`)를 지정했다면 맨 끝에 빈 줄을 두고 **지정된 문구 그대로** 추가한다. 지정이 없으면 임의로 만들어 붙이지 않는다.

## 타입

| 타입       | 사용 시점                                               |
| ---------- | ------------------------------------------------------- |
| `feat`     | 새로운 기능·화면·컴포넌트 추가                          |
| `fix`      | 버그 수정                                               |
| `docs`     | 문서 수정 (README, CLAUDE.md 등. 코드 변경 없음)        |
| `style`    | 포맷팅 등 동작에 영향 없는 스타일 변경                  |
| `refactor` | 동작 변경 없는 구조 개선                                |
| `test`     | 테스트 추가/수정                                        |
| `perf`     | 성능 개선                                               |
| `revert`   | 이전 커밋 되돌리기 (`revert: feat: 원래 제목`)          |
| `chore`    | 의존성, 빌드/도구 설정, `.gitignore`, `.claude` 설정 등 |

타입이 애매하면 "사용자에게 보이는 동작이 바뀌었는가?"를 기준으로 한다. 바뀌었다면 `feat`/`fix`, 아니라면 `refactor`/`chore`/`docs`다.

- UI 문구·스타일 수정처럼 보이는 것이 바뀌면 `style`이 아니라 `feat`/`fix`다 (`style`은 공백·세미콜론·정렬 같은 코드 포맷 한정).
- `package.json`의 의존성 변경은 `chore(deps)`, 그 의존성을 쓰는 코드와 한 묶음이면 기능 커밋에 포함해도 된다.
- `revert` 본문에는 되돌리는 커밋 해시와 이유를 적는다.

## 첫 커밋 / 대량 변경

저장소에 커밋이 없고 파일이 대량으로 untracked인 경우(프로젝트 초기 세팅):

- 전부를 한 커밋에 넣지 말고, 성격별로 나누는 것을 제안한다. 예시 순서:
  1. `chore: Next.js + Supabase 프로젝트 초기 세팅` (루트 설정 파일, `package.json`, `.gitignore`)
  2. `feat: 앱 라우트 및 인증 흐름 구성` (`app/`, `lib/supabase/`, `proxy.ts`)
  3. `feat(ui): shadcn/ui 컴포넌트 추가` (`components/ui/`, `components.json`)
  4. `chore(claude): Claude Code 스킬 및 MCP 설정 추가` (`.claude/`, `.mcp.json`, `.agents/`, `skills-lock.json`)
- 사용자가 "한 번에" 커밋하길 원하면 따르되, `chore: 프로젝트 초기 세팅`처럼 제목을 포괄적으로 쓰고 본문에 구성 요소를 불릿으로 요약한다.
- 4번 안전 점검을 특히 엄격히 한다. `.claude/settings.local.json`은 개인 설정일 수 있으므로 커밋 여부를 사용자에게 확인한다 (`.gitignore` 대상인지 먼저 확인).

## amend와 히스토리 수정

- 사용자가 명시적으로 요청하지 않으면 `--amend`, `rebase`, `reset --hard`, `push --force`를 쓰지 않는다.
- amend 요청 시: 직전 커밋이 **push되지 않았는지** 확인한다 (`git status`의 ahead/upstream 정보). push된 커밋이면 히스토리 재작성의 영향을 설명하고 확인을 받는다.
- 메시지만 고치는 경우도 새 attribution 트레일러를 유지한다.

## 예시

| 변경사항                            | 커밋 메시지                                              |
| ----------------------------------- | -------------------------------------------------------- |
| shadcn 컴포넌트 추가                | `feat(ui): Select 컴포넌트 추가`                         |
| 인증 영역 버그 수정                 | `fix(auth): 로그아웃 후 보호 페이지 접근이 막히지 않는 문제 수정` |
| 여러 영역에 걸친 변경 (스코프 생략) | `feat: 앱 라우트(홈, 인증, 보호 페이지) 구성`            |
| 의존성                              | `chore(deps): next-themes, sonner 추가`                  |
| DB 변경                             | `feat(db): profiles 테이블 및 RLS 정책 추가`             |
| 문서                                | `docs: CLAUDE.md에 프로젝트 구조 및 명령어 추가`         |
| 설정                                | `chore: .gitignore에 Playwright 산출물 폴더 추가`        |
| Claude 설정                         | `chore(claude): git-commit 스킬 보강`                    |

본문이 필요한 경우:

```
fix: 토큰 만료 시 무한 리다이렉트 해결

- 갱신 로직이 만료 시각을 잘못 계산해 로그인 페이지로 반복 이동하던 문제 수정
- 만료 직전 요청에서도 갱신되도록 여유 시간 추가

Fixes #456
```

Breaking change가 있는 경우:

```
feat(db)!: profiles.name 컬럼을 display_name으로 변경

- 화면 표시용 이름과 로그인 식별자를 분리하기 위해 컬럼명 변경

BREAKING CHANGE: 배포 전 마이그레이션 적용 필요. 기존 `name` 조회 쿼리는 `display_name`으로 교체해야 함.
```

## 피해야 할 메시지

- 모호함: `fix: 버그 수정`, `update code`, `chore: 수정` (무엇이 바뀌었는지 알 수 없음)
- 여러 변경 혼합: `feat: 로그인 추가 및 버그 수정 및 문서 업데이트` (나눠서 커밋)
- 지나치게 긴 제목: 세부 내용은 본문으로 보낸다.
- 파일 나열형 본문: `- a.tsx 수정`, `- b.ts 수정` (diff가 이미 보여줌)
- 추측성 이유: diff에서 확인되지 않은 의도·효과를 사실처럼 쓰지 않는다.
- 영어 동사로 시작하는 제목(`feat: add button`): 이 저장소는 한국어 명사형을 쓴다.

## 완료 보고

커밋을 수행했다면 짧게 보고한다: 커밋 해시(앞 7자리) + 제목, 포함된 파일 수, 제외한 파일과 그 이유(있다면), 남은 미커밋 변경(있다면). push하지 않았다면 그 사실도 한 줄로 밝힌다.
